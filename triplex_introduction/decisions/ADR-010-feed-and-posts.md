# ADR-010: Feed & posts — one cache, coalescing reactions, sheets as routes, photo viewer on gesture-handler

**Date:** 2026-10-03
**Status:** Accepted (iOS 26.5 verified; Android, iOS 18 and iPad **not** run — owner: "debug and test on iOS 26 only")
**Deciders:** Project owner (Task 7 of the migration plan; iOS 26 only), Claude (implementation)
**Context link:** [[ADR-005-rn-api-layer-and-error-model]], [[ADR-006-app-shell-and-navigation]], [[ADR-009-adaptive-controls-ios-native-android-drawn]]

---

## Context
Task 7 ports Flutter's feed: `PostCard`, `MediaGrid`, `FullScreenImageViewer`, reactions, repost, post detail. Flutter's version has defects the plan lists (hard-coded mock posts on any error/empty, `extra`-dependent detail, a stale detail card, fake share/saved counters) and subtler ones found while reading it against the backend (below). The backend (`triplex_node/controllers/postController.js`, `likeController.js`) has **no pagination** and returns the whole feed in one `GET posts/feed`.

## Decisions

1. **The query cache is the only place a post lives.** A post can be in the feed list, in its own detail entry, and embedded in a repost. Every change goes through `patchPost(queryClient, id, update)` (`model/postCache.ts`), which rewrites all of those copies and leaves untouched posts as the *same object* (so the list doesn't re-render them). Detail starts from the card the feed already has (`initialData`, marked stale) and then fetches `GET posts/:id` — it never needs `extra`, so `triplex://post/<id>` works from a cold start.
2. **Reactions are optimistic, serialised per post, and coalesce** (`model/reactionSync.ts`). A tap updates every cached copy at once; requests for one post run one after another and only the *last wish* is sent (👍 → ❤️ → 👍 while the first request is out sends at most one more). On failure the post snaps back to the last server-confirmed state and queued wishes are dropped. Why: concurrent POST/DELETE can be applied by the server in either order, and replaying wishes on top of a state that never happened is worse than reverting. The server's own `likes_count` replaces the guess when it answers. The backend's `POST likes/:id/like` **upserts** (the api_doc claim "selecting the same reaction removes it" is not true) — the *toggle is client-side*: tapping the heart with any reaction removes it; picking the reaction you already have removes it; removal sends `DELETE` with the server's current type in the body.
3. **Stale-while-revalidate across launches** is a small per-user snapshot in AsyncStorage (`model/feedSnapshot.ts`, newest 30 posts, zod-validated on read, removed on sign-out) written after each successful fetch and read into the cache **only if the network hasn't answered yet** (`updatedAt: 0`, so the running fetch still replaces it). Not `persistQueryClient`: that would persist every query for every user; this is one query, and a stale-shape snapshot is discarded rather than rendered.
4. **Wire → app model once, at the edge** (`model/schemas.ts`): zod transforms snake_case into the `Post` the UI uses. `pg` returns NUMERIC (`total_cost`, a stop's `cost`) and `COUNT(*)` as *strings* → lenient number converters (a malformed number is `null`/`0`, it never fails the feed). The author's **email is dropped** at the boundary (the backend sends it with every post). The nested original of a repost is exactly one level deep and may be `null` (deleted) — the schema is deliberately one level, and the card says "This post is no longer available".
5. **Reposting a repost reposts its *original*** (`repostTarget`). Flutter previews the original but posts a repost of the repost, and the backend nests only one level, so the chain renders an empty card. The sheet previews what will actually be reposted.
6. **Reactions list totals come from the per-type counts.** The server's `total` is the length of a user list capped at 50; the sheet shows the real sum and says "Showing the N most recent reactions" when it is capped.
7. **Reaction long-press has an accessible alternative:** the heart exposes the seven reactions as custom accessibility actions. The count next to it opens who reacted. Counts are not tinted by reaction (Flutter's amber/light-blue fail AA on white).
8. **Sheets and the viewer are routes**, registered at the root over the tabs: `reactions/[postId]` and `repost/[postId]` (native `formSheet`, via `useSheetOptions`), `image-viewer` (`transparentModal`, fade — the screen behind is what the backdrop blurs), `post/[id]` (pushed like Settings). **A formSheet that contains a ScrollView must have exactly two children — the header and the ScrollView — and the header needs `collapsable={false}`** or React Native flattens it away and the sheet lays the scroll content *over the header* (found on device; react-native-screens warns about it in the Metro log).
9. **Photo viewer = `react-native-gesture-handler` 2.32 + Reanimated 4.5.1** (Expo SDK 57's pinned versions; the project had drifted to 3.2.1 / 4.5.3 through expo-router's transitive deps — pinned back, native pods regenerated). Pinch about the fingers, pan while zoomed (with decay and bounds), double-tap, drag down/up to dismiss (backdrop blur and dim clear as you drag), paging with `FlatList`. The geometry is pure functions (`imageViewerMath.ts`, all worklets) so it is unit-tested. Photos travel as **one JSON-encoded route param** — Expo Router comma-joins an array param, which also splits Cloudinary URLs that contain commas (found on device) — and the parser accepts only `http(s)` URLs so a deep link can't make the viewer load `file://`.
10. **New design-system primitives** (each in the Gallery, light + dark): `Avatar`, `RemoteImage` (`expo-image`, disk cache, broken-image tile), `Chip`, `PageDots`, `ImageViewer`; `ListRow` gained a `leading` slot (people list); `TextField` gained an opt-in `multiline` mode (grows to three lines).
11. **The Feed tab's header title is the logo-font "Feed"** over a `ProgressiveBlur` strip, because photos scroll under the transparent header.

## Amendment 2026-10-03 (same day) — owner's UI refinement, Threads as the size/scale reference
The owner sent a Threads screenshot and asked for: no bold usernames, less-rounded media, the **Feed title to scroll with the list** (immersive, less chrome), **everyone's top reactions shown on reacted posts**, and **inset padding on the photo row that reaches the edge only while scrolling**. Result:
- **Type scale like Threads** (17-pt body): username `body` *medium* (500), time beside it on the same line in secondary colour, caption `body`, footer icons 22 pt with `callout` counts, avatar 40, trip-plan lines `body`; weights ≤ 500 across the feature (chips, counts, embedded names). The logo font only exists in bold, so the "Feed" wordmark stays bold but small (24).
- **Photos:** corner radius 12 (10 inside the embedded card, concentric with it); one photo is a 16:10 card inset 16 on both sides; several are **portrait 6:7 tiles at 62 % of the content width** in a full-width snapping `ScrollView` with `paddingHorizontal: 16` — at rest the first tile lines up with the text, and it slides under the screen edge as the row scrolls (`snapToInterval = tile + gap`). Dots follow the scroll; because the last tile can't reach the start edge, the last dot is chosen near the end of the scroll range (`pageIndexFor`).
- **Feed title is the list's first row** (`ListHeaderComponent`), the Feed stack has **no header**, a hairline separates posts, the footer is left-aligned like Threads. A `ProgressiveBlur` strip keeps the clock legible over scrolled photos.
- **Reaction cluster (owner's follow-up: "heart and reactions preview together in one overlapping row, heart on top; once reacted, the heart is replaced by the reaction"):** the footer's reaction control is one overlapping row (`CircleStack`, 30-pt slots cut out of each other, first in front). **The front slot is the like button** — the outline heart, or *your reaction's emoji* once you have reacted (never both) — and up to two *other* top reactions (`otherReactionTypes`, the user's own excluded) peek out behind it, followed by the count. The feed only has a count, so a card with reactions lazily asks `GET likes/:id/likes` (same cache entry as the sheet; silent on failure; 60 s fresh) and refetches when a reaction settles (`ReactionSync.onConverged`). Cost: one small request per on-screen card that has reactions; **a per-type breakdown in the feed payload would remove it** (TODO-003). Primitives: `CircleStack`, `EmojiBadge`, `EmojiStack` (all in the Gallery). Found while testing it: `ReactionSync` re-sent the same request forever if the server answered with a *different* reaction than asked (out-of-memory in a test) — the server's answer is now taken as the truth and a changed wish is still followed (2 regression tests).
- **Gotcha:** after the dependency pins changed, a long-running Metro served cached transforms stamped with the *old* Worklets Babel plugin → red screen "Mismatch between JavaScript code version and Worklets Babel plugin version (0.10.1 vs. 0.10.4)". **Restart Metro with `--clear`** after any change to `react-native-worklets` / `reanimated` versions.

## Differences from Flutter (deliberate)
Real empty / offline / error states instead of mock posts; no share / saved counters (the backend has neither) and no comment-preview pill (the backend never sends one); trip stop names are plain bold text, not blue-underlined "links" that go nowhere; cost is formatted from the real `USD`-style currency (`$1.50`), not Flutter's `toStringAsFixed(0)` + `+` (which printed `2USD+` for real data); reaction counts aren't tinted; all seven reactions are in the picker (Flutter showed six); media is photos only (Task 10); the avatar / username on a card are **not** tappable yet (profile screens are Task 9); the comment count opens the post (the comments list arrives in Task 8).

## Consequences
- New native dependency: **`expo-image`** (dev client rebuilt, `expo prebuild --platform ios` + `pod install` with a UTF-8 locale). `react-native-gesture-handler`, `react-native-reanimated`, `react-native-worklets` are now direct dependencies at Expo's pinned versions (they were already linked).
- The feed is **one unpaginated request** and the backend does N+1 queries per post. Fine for today's data; needs cursor pagination in the backend before it can scale (plan §8) — [[todo/TODO-003-feed-backend-limits]].
- Not verified: Android, iOS 18, iPad; offline / error / empty feed *on device* (unit-tested); the double-tap zoom on device (the simulator tool can't tap twice within 250 ms — the maths is unit-tested); Reduce Motion; VoiceOver with a real screen reader; a long feed's scroll performance (9 posts locally).
