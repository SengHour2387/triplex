# Triplex App Architecture

This document outlines the architectural patterns, state management, directory structure, and key libraries used in the Triplex Flutter application. It serves as a guide for understanding how to add or modify features without breaking the existing architecture.

## Tech Stack & Libraries
- **Framework:** Flutter
- **State Management & DI:** `flutter_riverpod` (v3), `riverpod_annotation`, `riverpod_generator`
- **Routing:** `go_router`
- **Networking:** `dio` & `http` (with `dio_cache_interceptor`)
- **Local Database:** `drift` (SQLite)
- **Secure Storage:** `flutter_secure_storage` (for JWT tokens)
- **Data Models:** `freezed_annotation`, `json_annotation`
- **Functional Programming:** `fpdart` (for `Either`, `Option` types)
- **UI & Media:** `google_maps_flutter`, `cached_network_image`, `progressive_blur`, `flutter_animate`, etc.

## Directory Structure
The app strictly follows a **Feature-First Clean Architecture**.

```text
lib/
├── app.dart              # Main App widget and setup
├── main.dart             # Entry point
├── core/                 # Global, cross-feature utilities and services
│   ├── api/              # Dio providers, auth interceptors
│   ├── cache/            # Caching strategies
│   ├── config/           # App configuration (e.g., base URLs)
│   ├── database/         # Drift local database setup
│   ├── navigation/       # Navigation helpers
│   ├── router/           # GoRouter configuration
│   ├── storage/          # Secure storage providers
│   ├── toast/            # Global toast notifications
│   └── widgets/          # Shared, generic UI components
└── features/             # Feature modules (auth, feed, profile, map, etc.)
    └── [feature_name]/   
        ├── data/         # Repositories (API calls, DB queries)
        ├── domain/       # Riverpod Notifiers (State + Business Logic), Models
        └── presentation/ # Screens and feature-specific Widgets
```

## Layer Responsibilities (Inside `features/`)

### 1. `data/`
Contains **Repositories** (`[feature]_repo.dart`).
- Responsible for fetching and sending data to external sources (REST APIs via `Dio` or local DB via `Drift`).
- Repositories are exposed as Riverpod providers.
- **Rule:** Repositories should not hold application state. They just return data or throw errors.

### 2. `domain/`
Contains **Models** and **Riverpod Notifiers** (`[feature]_notifier.dart`).
- **Models:** Freezed/JsonSerializable data classes (e.g., `user_model.dart`).
- **Notifiers:** Handle business logic and application state.
- **Rule:** Notifiers interact with Repositories to fetch data and update their `state`. This is where `AsyncValue` (Loading, Data, Error) is managed.

### 3. `presentation/`
Contains **Screens** and **Widgets**.
- `screens/`: Full-page views routed via `go_router`.
- `widgets/`: Local UI components specific to the feature.
- **Rule:** UI components should be as dumb as possible. They listen to Notifiers via `ref.watch()` and trigger actions via `ref.read().method()`.

## Key Architectural Patterns

### Authentication & API Interception
- The app uses JWT tokens.
- `Dio` is configured globally in `core/api/dio_provider.dart`.
- `AuthInterceptor` (`core/api/auth_interceptor.dart`) automatically injects the `Authorization: Bearer <token>` header.
- **Token Refresh:** If an API returns `401` or `403`, `AuthInterceptor` pauses outgoing requests, refreshes the token using the refresh token, stores the new tokens, and retries the failed requests.

### State Management (Riverpod)
- All providers and notifiers use code generation (`@riverpod` or `@Riverpod(keepAlive: true)`).
- Run `dart run build_runner watch -d` when adding or modifying providers, models, or database schemas.
- Business logic resides in `_$Notifier` classes generated by Riverpod.

### Local Database
- Powered by `Drift`.
- Managed in `core/database/app_database.dart`.

## Adding a New Feature (Workflow)
1. **Create the folder:** `lib/features/[feature_name]/` with `data`, `domain`, and `presentation` subfolders.
2. **Define Models (`domain/`):** Create the data entities using `@freezed` or `@JsonSerializable`.
3. **Build Repository (`data/`):** Create a repository class with a provider to handle Dio API calls.
4. **Create Notifier (`domain/`):** Create a Riverpod Notifier to manage the feature's state, injecting the repository via `ref.read()`.
5. **Build UI (`presentation/`):** Create the screens and bind them to the Notifier state.
6. **Add to Router:** Register the new screen(s) in `core/router/`.
